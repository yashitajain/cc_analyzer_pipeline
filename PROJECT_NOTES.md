# CC Statement Analyzer — Project Notes

Living backlog + architecture map. Read this before recommending changes; re-check the actual code before trusting anything below as still accurate.

## Stack
- Frontend: Streamlit (`app.py`), custom theme (`theme.py`, `.streamlit/config.toml`)
- Extraction: pdfplumber + Claude API (`backend/extract.py`)
- Storage: Supabase/PostgreSQL (raw_transactions, processed_files, households, household_members)
- Analytics: `backend/analytics.py`
- Household sharing: `backend/household.py` (lightweight, no-token invites)
- Notifications: `backend/notifications.py` (Gmail SMTP invite emails)

## Architecture map
- `app.py` — auth/session setup, `_ensure_household_schema()`, `load_data()` / `load_clean_transactions()`, 6 sections navigated via a sidebar radio (`active_section`), not tabs: Overview, Category, Anomalies, Budget Tracker, Transactions, Ask AI
- `backend/extract.py` — `extract_text()` (per-page extraction, dedupes repeated header/footer lines across pages), `parse_with_ai()` (Claude call, compact `[date, merchant, category, amount, is_credit]` row format), `validate_transactions()` (per-row field checks + statement-level control total, `control_ok` = |extracted_total - statement_total| <= $5), `process_single_pdf()` (orchestrates extract -> parse -> validate -> save, per-user dedup via `processed_files`)
- `backend/analytics.py` — `load_raw_transactions()`, `clean_transactions()`, `monthly_summary()`, `category_spend()`, `detect_anomalies()`, `member_spend()`
- `backend/household.py` — one household per user; pending invites activate on the invitee's first Google sign-in
- `backend/budgets.py` — budget persistence, keyed by (user_email, month); `get_budget_for_month()` carries forward the most recent prior month's numbers when the requested month has no saved row yet
- `backend/notifications.py` — best-effort invite email over Gmail SMTP, never raises

## Backlog (proposed, not yet built)
- [ ] Build real "Ask AI" free-text Q&A over spending data -- currently just an honest placeholder (see 2026-10-01 log entry), not the actual feature.
- [ ] Recurring-charge / subscription detection -- group by merchant + similar amount recurring monthly (there's already a "Subscription" category to anchor this).
- [ ] Card/account-level breakdown -- today the only way to distinguish statements is `source_file`; tagging card issuer or last 4 digits during extraction would let "spend by card" be a real filter.
- [ ] Monthly recap email -- reuse the existing Gmail SMTP in `backend/notifications.py` (currently only used for household invites) to send a monthly spend summary.
- [ ] Processing-metrics trend view -- now that latency_ms/input_tokens/output_tokens/estimated_cost_usd/validation_index are stored per file in `processed_files`, a small chart of them over time (e.g. in an admin-style tab) would show extraction cost/speed/quality drifting before it becomes an obvious problem.
- [ ] Transaction-count cross-check — most statements print a count near the summary; capture it in the extraction prompt and compare to `len(transactions)` in `validate_transactions()`. Catches a duplicate+omission pair that nets to zero on the dollar total.
- [ ] Surface per-row `errors` in the UI even when `control_ok` is True (currently computed but not shown as a "review this" signal on its own).
- [ ] "Review flagged" view — list every processed file where `control_ok` was False, so flagged statements don't rely on being noticed at upload time.
- [ ] Configurable control-total tolerance (currently hardcoded at $5 in `validate_transactions()`).

## Decisions / resolved issues log
- 2026-10-01: Fixed Budget Tracker fields getting stuck on hardcoded defaults instead of the saved budget. Root cause: Streamlit ignores a widget's `value=` argument on every render after the first time that widget's `key` exists in `st.session_state` -- since `salary_{month_key}` etc. keys never change, the very first time a given month was opened (before anything had been saved for it) permanently locked that month's widgets to the hardcoded default for the rest of the browser session, no matter what `get_budget_for_month()` returned afterward. Fixed by seeding `st.session_state` directly from the loaded budget exactly once per month (guarded by a `_budget_loaded_{month_key}` flag) before any widget with those keys is created, and removing the now-redundant (and previously ineffective) `value=` arguments from the number_inputs/sliders -- they read purely from session_state now. `max_value` on the sliders is unaffected since only `value` is subject to this Streamlit behavior.
- 2026-10-01: Fixed `NameError: name 'category_df' is not defined` in Budget Tracker -- caused by the tabs-to-sidebar-nav change above. `st.tabs()` runs every tab's body on every rerun regardless of which tab is visible, so `category_df` (computed inside the old Category tab) was silently available to Budget Tracker's code too. A real `if/elif` only executes the selected branch, so once tabs became sections, `category_df` stopped existing whenever Budget Tracker was selected without Category having run first in that session. Fixed by hoisting `category_df = category_spend(...)` above the if/elif chain so it's always computed once per rerun regardless of which section is active, and removing the now-redundant copy that used to live inside the Category branch. Checked every other per-section dataframe (summary_df/anomaly_df/member_df/plan_month_df/variable_df/filtered_df/display_df) and confirmed none of them are referenced outside their own section, so this was the only cross-section dependency.
- 2026-10-01: Replaced the 6 horizontal `st.tabs()` with a vertical sidebar nav (`st.sidebar.radio`, key `active_section`) for better organization with six sections. Each former `with tabN:` became an `if/elif section == "...":` branch -- same bodies, untouched. Added CSS in `theme.py` scoped to `[data-testid="stSidebar"]` so the nav stacks vertically instead of inheriting the pill/inline-flex style built for the 2-option My Spend/Household Spend toggle (that toggle itself is unaffected, the override is sidebar-only). Also gave the "Ask AI" section an honest placeholder message instead of silently rendering nothing -- it was never actually a bug in this file, there was simply no `with tab6:` body at all; the real feature is still on the backlog.
- 2026-10-01: Moved the budget Save button up again -- it was sitting after the category budget sliders (still "before Variable Costs" as asked, but visually far down the tab). Moved `st.form_submit_button` to render immediately under the fixed-cost inputs, before the "Variable Cost Budget Targets" sliders even start. A form's submit button can sit anywhere inside the form and still submits everything in it, so this didn't change what gets saved -- just where the button appears.
- 2026-10-01: Stopped Budget Tracker from recomputing on every keystroke -- Income/Fixed Costs and the category budget sliders are now wrapped in a single `st.form(key=f"budget_form_{month_key}")`, so typing into e.g. Mortgage no longer triggers a script rerun (and therefore no Monthly Summary/Budget vs Actual recompute) until "Save this month's budget" (now `st.form_submit_button`) is pressed. That button sits right after the fixed-cost inputs and budget sliders, before the "Variable Costs" section, instead of at the very bottom of the tab. Save confirmation moved from an inline `st.success()` to `st.toast()` since the button no longer sits directly above Monthly Summary, where the old message rendered.
- 2026-10-01: Made the Budget Tracker tab actually persistent -- added `backend/budgets.py` and a `budgets` table (user_email, month, fixed costs, category_budgets as JSONB, savings, savings_rate; PRIMARY KEY (user_email, month)). Before this, every number in tab4 (salary, mortgage, utilities, category sliders) was a plain Streamlit widget with a hardcoded default -- nothing was saved, so every new session reset back to the same $5,000 salary / $2,000 mortgage regardless of what the user had entered. Now `get_budget_for_month()` loads the saved budget for the selected month, falling back to the most recent prior month's budget if this exact month hasn't been saved yet ("if not changed, keep the fixed costs as they were") -- a caption tells the user which case they're in. All widgets got month-scoped keys (e.g. `salary_{month_key}`) so switching the month selector actually refreshes every field instead of Streamlit holding onto whatever was last typed under the old unscoped key. A "Save this month's budget" button persists fixed costs + category targets + the computed savings/savings_rate via `save_budget()` (upsert). The month selector now also always includes the current calendar month even before any statements exist for it, so a budget can be set up in advance. `get_savings_history()` exists for a future savings-over-time view but isn't wired into the UI yet.
- 2026-09-30: Fixed "processing results never show up" -- the Process Statements button handler rendered the whole "Processing Results" section (per-file expanders, control-total check, the new latency/cost/validation index metrics) and then called `st.session_state.analyzed = True; st.rerun()` immediately after, which replaces the entire script output right away -- so that section never actually reached the screen, it just flashed and got overwritten by the tabs view. Fixed by stashing `results_list` in `st.session_state.last_upload_results` instead of rendering it inline, then rendering it (via a shared `render_processing_results()` helper) as a persistent banner at the top of the tabs view, with a Dismiss button and cleared on "Upload more" too. This means the per-file metrics added earlier today were never actually visible until this fix.
- 2026-09-30: Added per-file processing metrics -- `parse_with_ai()` now times the Claude API call and reads `message.usage` for input/output token counts, computing `estimated_cost_usd` from Sonnet 4.5's published rates ($3/MTok in, $15/MTok out, checked against platform.claude.com/docs pricing). `validate_transactions()` gained a `validation_index` (0-1, row-validity ratio x control-total closeness) that degrades smoothly instead of just flipping `control_ok`. Both are persisted on `processed_files` (new nullable columns: latency_ms, input_tokens, output_tokens, estimated_cost_usd, validation_index, self-healed via ALTER TABLE ADD COLUMN IF NOT EXISTS) and shown per file in the Processing Results expander in app.py. Older processed_files rows will show NULL for these since they predate this change.
- 2026-09-30: Fixed "data disappears after logging back in" -- it wasn't data loss. `df = load_data(selected_emails)` already loaded real transactions from Supabase on every run, but `st.session_state.analyzed` hardcoded to `False` on every fresh browser session, so returning users always landed on the Step 1/Step 3 upload screen (summary tiles only) instead of the tabs, even with months of data saved. Changed the init to `st.session_state.analyzed = df is not None and not df.empty`, so a returning user with existing data lands straight on the Overview/Category/Anomalies/Budget/Transactions/Ask AI tabs. "Upload more" still resets it to False as before.
- 2026-09-30: Cut extraction cost/latency — `extract_text()` now dedupes boilerplate lines repeated across pages before sending to Claude; `parse_with_ai()` switched transaction rows from per-field objects to compact arrays; `process_single_pdf()` converts rows back via `_rows_to_transactions()` so nothing downstream changed. Not yet re-verified by spot-check against a known-good statement post-change.
- Earlier: resolved DuckDB -> PostgreSQL migration, dbt schema misconfiguration, Supabase connection setup issues.

## Known constraints / accepted tradeoffs
- `user_email` required everywhere transactions are saved — no anonymous/unscoped writes.
- Household invites have no email verification token — accepted risk for a trusted small-household use case.
- `GMAIL_APP_PASSWORD` sourced from env; email send is best-effort and never blocks the invite itself.
